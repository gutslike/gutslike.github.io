A **soft 404** is a page that tells the user "this doesn't exist" while telling the network "200 OK". The human is informed; every machine is misled.

In this post I cover two variants of it. The second one was considerably worse than it first appeared, and I found it by accident.

---

## Concept: the status code is the API

An HTTP status is not decoration. It is the only part of the response that automated consumers are guaranteed to read and act on.

| Code | Means | What a crawler does |
|---|---|---|
| 200 | Here is the resource | Index it; come back later; follow its links |
| 301 / 308 | It moved, permanently | Transfer signals to the new URL; stop asking |
| 404 | No such resource | Drop it from the index; stop asking |
| 410 | Gone, deliberately | As 404, but stronger |

A soft 404 breaks the contract in the most expensive direction. The crawler believes an unbounded set of URLs are real pages, so it:

- spends crawl budget re-fetching pages that carry nothing,
- indexes near-identical thin pages that compete with your real ones,
- and keeps doing both, because nothing ever tells it to stop.

Search consoles report these under labels like *"Soft 404"* precisely because engines have to detect them heuristically — the server never said anything was wrong.

## Variant 1: detail pages that never checked

The pattern was the ordinary one:

```tsx
export default function ProfilePage({ params }) {
  const { username } = params;
  return <ProfileView username={username} />;   // fetches client-side
}
```

Invent a username and you get a perfectly successful page about nobody. The component fetches, gets nothing, and renders an empty state — at 200.

### Why the obvious fix does not work here

The recommendation was "call `notFound()` on these four routes." Three of the four were `"use client"`, and that is a hard blocker:

**A client component cannot set an HTTP status.** By the time it runs, the response headers are long gone. It can draw a not-found *screen* on top of an already-sent 200, which is exactly the bug.

Setting a status requires a server component, which means either converting the route or wrapping it. I converted the two thin client wrappers:

```tsx
// Server component: the check happens before anything is sent
export default async function ProfilePage({ params }) {
  const { username } = await params;

  const user = await prisma.user.findUnique({
    where: { username },
    select: { id: true },
  });

  if (!user) {
    notFound();      // throws; the framework converts it to a real 404
  }

  return <ProfileView username={username} />;   // still a client component
}
```

For a 500-line client page, converting it would have been reckless, so I put a server `layout.tsx` beside it instead. It does the same job — the layout runs on the server, checks existence, and throws before the page renders:

```tsx
export default async function CertificateLayout({ params, children }) {
  const { id } = await params;
  const record = await prisma.certificate.findUnique({ where: { id } });
  if (!record) notFound();
  return <>{children}</>;
}
```

> A server layout beside a client page is the cheap way to add server-side behaviour to a page you do not want to rewrite.

### The bug that testing could not have caught

I first wrote the certificate check as:

```ts
where: { certificateId: id }      // the URL segment is named certificateId
```

That is the obvious reading. But the API serving the same records looked up a **different column**, plus an active-and-not-revoked filter. My naive version would have 404'd **every real certificate**.

No local test could have caught it: that table was empty in development, so both versions returned "not found" for every input and looked identical. I found it by reading the API that already worked.

> **When a table is empty locally, your tests agree with every hypothesis.** Verify against the code that already handles the data, not against a passing run.

### One route was already correct

One page had called `notFound()` for months and still returned 200 in production — because of the SSR bug in [post 1](/blog/debugging/seo-optimisation/01-the-three-line-bug/). `notFound()` works by throwing during render. The provider discarded the subtree, so the page component never rendered, so nothing threw, so the framework returned 200 for a page it had never executed.

Fixing the upstream bug repaired this one for free.

## Variant 2: a dynamic segment that matched everything

This one started as a trivial ticket — *"the PWA manifest 404s"* — and turned out to be the interesting bug of the set.

The layout declared four static resources:

```ts
manifest: "/manifest.json",
icons: {
  icon: ["/favicon.ico", "/icon.png"],
  apple: ["/apple-icon.png"],
},
```

Three of the four files did not exist. But they did not 404 either:

```text
/manifest.json      200  text/html  224340B
/icon.png           200  text/html  224313B
/nonexistent.json   200  text/html  224385B
/foo.php            200  text/html  224286B
```

224 KB of `text/html` for a file that does not exist — **that is the homepage**, served at 200, at every one of those URLs.

### Cause, in two parts

**Part one: the middleware never saw the request.** The matcher excluded any path containing a dot:

```ts
export const config = {
  matcher: ["/((?!_next|assets|.*\\..*$).*)"],
};
```

That exclusion is normal and usually correct — you do not want locale-rewriting logic running on `.png` and `.css` requests. But it means every dotted path skips the middleware entirely.

**Part two: the route segment matched it anyway.** The app is organised as `app/[lang]/...`, and `[lang]` is a **dynamic segment that matches any single path segment**. Not "any locale" — *any segment*. Including `manifest.json`.

There was a `generateStaticParams` listing the seven real locales, which is easy to mistake for a constraint. It is not:

> `generateStaticParams` says *"prerender these at build time."* It does **not** say *"reject anything else."* That is `dynamicParams`, which defaults to `true` — meaning unlisted values are rendered on demand.

So the request reached the layout with the locale set to `"manifest.json"`, nothing validated it, and Next rendered the homepage. Status 200.

The blast radius was not one file. **Every unknown dotted path on the site was an indexable 200-status duplicate of the homepage** — an unbounded set of them, at arbitrary URLs, discoverable by any bad link anywhere on the internet.

### The fix, and the fix I rejected

The obvious fix is `export const dynamicParams = false`. I rejected it.

**Route segment config is inherited by child segments.** Setting it on the locale segment would also have applied to `[slug]` detail pages beneath it — meaning any record created *after* the last build would 404 until the next deploy. That trades a crawler problem for a customer-facing one.

An explicit check affects only the segment it is written in:

```tsx
export default async function LangLayout({ params, children }) {
  const { lang } = await params;

  if (!locales.includes(lang)) {
    notFound();
  }

  return <Providers lang={lang}>{children}</Providers>;
}
```

Plus, of course, I actually created the declared files.

The result:

```text
/manifest.json      200  application/json      (and it parses)
/nonexistent.json   404
/foo.php            404
/wp-login.php       404
```

## A generalisable check

Any dynamic segment near the root of your route tree matches more than you think. Ask of each one:

1. What is the **full set** of values this segment accepts? (Answer: every string, unless you check.)
2. What happens for a value outside the set you had in mind?
3. Is that answer a **status code**, or just a screen?

And test it the way a crawler would:

```bash
for p in /manifest.json /nonexistent.json /foo.php /wp-login.php /.env; do
  printf '%-22s ' "$p"
  curl -s -o /dev/null -w '%{http_code} %{content_type} %{size_download}B\n' "https://example.com$p"
done
```

Any 200 with `text/html` and a suspiciously round size is your homepage wearing a disguise.

## Takeaways

1. **A client component cannot set a status code.** Not-found *screens* are not not-found *responses*.
2. **`generateStaticParams` is not validation.** Unlisted params still render unless `dynamicParams` is false — and that setting is inherited, so prefer an explicit check.
3. **Middleware matchers that exclude dots** leave a whole class of paths to your route tree. Know what catches them.
4. **Empty tables make every hypothesis pass.** Verify against working code.
5. Fix the upstream renderer first — some soft 404s are symptoms, not causes.
